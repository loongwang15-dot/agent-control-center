### 选型结论

- 上游 README 将团队管理 MCP 入口描述为 Claude Desktop；Codex 主要通过 CodexDriver 作为被调度 Agent。它没有证明 Codex 桌面主控能开箱即用地调用 `create_team`、审核和释放 Agent。
- CodexDriver 默认 `approvalPolicy: "never"`，并自动接受命令执行、文件修改、补丁、MCP elicitation 和权限请求；默认还给 Codex 子任务 workspace-write 与网络权限。本轮不应按原样启动。
- 上游测试源码含 Unix 路径、`which` 和 `bun` 命令查找假设。为隔离用户数据，测试时将 `HOME` 重定向到 `.tools/multiagents-main/.sandbox-home`，并仅在本地副本把 `/tmp` 测试目录改为 `os.tmpdir()`。
- 调整测试目录后，上游套件结果为 **115 通过、8 失败（123 项）**。剩余失败反映 Windows 命令查找/脚本兼容问题；完整 multiagents 团队派发未在本机运行。
- 判断：可作为后续研究的 peer/worker 协作候选，但当前版不是已验证的 Codex 主控方案；需要先实现 Codex 主控适配，并把子 Agent 权限改为显式最小权限。

## Playwright 上传与手动操作失效：根因调查（2026-10-20）

### 本机证据

- 本项目使用 `@playwright/mcp` `0.0.83`，通过 `.codex/config.toml` 的 `--extension` 接入 Chrome 已登录页面。
- 上传按钮点击确实触发 Playwright 的 File chooser 状态；上传文件时返回 `DOM.setFileInputFiles: Not allowed`。之后 MCP 多次保留 `[File chooser]: can be handled by browser_file_upload`，另有一次报告“only be used when there is related modal state present”。这不只是 Lovart 的特定网页控件，因为失败发生在浏览器协议向 file input 设置本地文件的阶段。
- 用户实测：扩展控制连接释放后，人工文件选择可用；控制期间再次点击上传按钮无响应。记录中没有 OS 文件选择窗口可见状态或浏览器窗口层级证据，故不能断言当时一定存在可见的原生文件对话框。
- 浏览器清单区分出两个扩展 ID：Playwright MCP 接入的实际 Chrome 有 `chrome-extension://mmlmfjhmonkocbjadbfplnigmagldckm/status.html` 状态标签；当前 ChatGPT in-app browser 打开的 `chrome://extensions/?id=jambeljnbnfbkcpnoiaedcabbgmnnlcd` 属于另一个浏览器面板/扩展上下文。不能误把后者当作本项目 Chrome 中的 MCP Bridge 设置页。

### 对自动上传错误的原因判断

- **高度匹配的上游已知问题（本机权限值尚未核验）：**Microsoft Playwright 官方仓库问题 #1481 报告同一错误：在 `--extension` 桥接模式，即便用最小页面的 `input[type=file]`，`setInputFiles()` 也会抛出 `DOM.setFileInputFiles ... Not allowed`；相同操作在非扩展 Edge 成功。维护者答复指出扩展默认没有文件访问权限，应在该扩展详情页打开“Allow access to file URLs”。这与本机错误逐字匹配，但本机设置值尚未读取，所以这是最可能根因，不是本机修复已验证。来源：[Playwright MCP issue #1481](https://github.com/microsoft/playwright-mcp/issues/1481)。
- Chrome 官方扩展文档说明，访问 `file://` 资源需由用户在扩展详情页授权“Allow access to file URLs”。来源：[Declare permissions – Chrome for Developers](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions)。
- 上游维护者也列出 Chrome 启动参数 `--disable-extensions-file-access-check`，但它关闭全部扩展的文件访问检查，范围大于只给 Playwright Bridge 单独授权；不建议采用。

### 对“扩展控制期间手动上传失效”的原因判断

- **最可能的直接触发因素：未消费的 File chooser / 选择器拦截状态。**Playwright 官方 issue #1481 另记录上传工具可能消费首个 queued chooser modal state，重复点上传可能积累 stale chooser 状态。本机恰好观察到 chooser 一直存在、上传被 Not allowed、重复操作后出现 modal state 不匹配；释放控制后人工上传成功。该证据支持“当前页面已处于等待文件选择的拦截/模态状态，人工新点击不能开启一个干净的新选择流程”，比“Playwright 扩展普遍禁用鼠标点击”更符合现象。
- **尚未证实具体呈现形式：**目前没有记录到系统级文件选择窗口是否可见、是否被其他窗口遮挡，也没有在同一重现中记录断开 MCP 连接前后的 chooser 事件队列。因此“用户手动点击被原生文件选择窗口模态阻塞”仍是推断；确定的是 MCP 侧 chooser 状态曾持续存在。Chrome `chrome.debugger` 文档只说明扩展以 CDP transport 接管标签调试，不表明调试器附着本身会普遍禁用人工鼠标输入。来源：[Chrome debugger API](https://developer.chrome.com/docs/extensions/reference/api/debugger)。

### 建议的修复与验证顺序（尚未执行）

1. 在**实际连接的 Chrome profile**打开 Playwright MCP Bridge（本机桥接 ID `mmlmfjhmonkocbjadbfplnigmagldckm`）的扩展详情，核实并开启“Allow access to file URLs”。当前 IAB 的 `jambelj...` 扩展页面不是该桥接 ID。
2. 重连后只触发一次 Lovart 文件选择；对一个 File chooser 只调用一次 `browser_file_upload`。确认上传按钮的 `<input type=file>` 收到文件，并在页面输入区看到对应缩略图后才记作成功。不要为“清理状态”连续点上传或发送空路径。
3. 如上传工具报错或 chooser 留存，立即停手并记录页面/窗口状态；断开扩展控制后再人工完成一次选择。避免在不确定状态下累积 chooser。
4. 如果已开启扩展文件访问权限仍然失败，使用受控最小复现对比：同一个空白 `input[type=file]`，分别跑 extension 与普通 Playwright/CDP 模式。普通模式成功而 extension 模式失败，则升级/报告 MCP Bridge relay 的权限兼容问题；不要用关闭全局扩展文件访问检查的启动开关绕过。

**结论等级：**自动上传错误已有高度匹配的上游根因与针对性设置建议，但本机权限开关尚未查看/修改/复测；手动点击失效与陈旧 File chooser 状态高度相关，根因的 OS 窗口层尚未证实。以上均保留为待验证项，未记为修复成功。
